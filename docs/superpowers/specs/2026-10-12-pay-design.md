# 支付模块设计（P3 第 1 项）

> 状态：已确认（2026-10-12）
> 上游：[总体设计](2026-09-07-ccloud-design.md) 的 P3「module-pay（微信/支付宝/钱包/退款/转账/回调重试）」与第 6 节「跨服务一致性」。P1 已交付 pay 的表结构（`sql/mysql/ddl/05-pay.sql`）、菜单、字典与演示数据；P2 已交付开放平台的签名调用与回调通知。

## 1. 目标与范围

新建 `ccloud-module-pay`（`pay-api` + `pay-biz`），服务名 `ccloud-pay-server`，端口 28085。提供与渠道无关的支付中心：支付应用、渠道配置、支付单、退款单、转账单、钱包与充值。本期用 Mock 渠道和钱包渠道在本地完整走通「下单 → 支付 → 通知 → 退款 → 转账」；以后接聚合支付或直连微信、支付宝时，只需新增一个渠道实现。

### 1.1 已确认的取舍

| 问题 | 结论 |
|---|---|
| 渠道实现 | 只做 Mock 与钱包。具体用哪家聚合支付未定，也可能直连；渠道接口同时兼容「一个渠道一种支付方式」（直连）和「一个渠道多种支付方式」（聚合） |
| 渠道层位置 | 放在 pay-biz 的 `framework/pay/core/client` 包，与 system 的短信客户端、infra 的文件客户端结构一致，不做成框架 starter |
| 通知内部服务 | 状态变更与 outbox 消息同一事务提交，经 Redis Stream 投递，消费方用 `IdempotentConsumer` 幂等 |
| 通知外部系统 | 外部系统只经开放平台接入：支付应用绑定开放应用，经 `OpenNotifyApi` 回调，签名与重试由 open 负责。删除 `pay_notify_task`、`pay_notify_log` 两张表与所有回调地址字段 |
| 外部系统调用 | 开放接口 `/open-api/pay/**`：创建/查询支付单、提交支付（不可选钱包）、发起/查询退款。转账不开放 |
| 钱包 | 充值（套餐赠送或自定义金额）、余额支付、退款退回、充值退款、后台调整余额。不做提现，`freeze_price` 本期不用 |
| 重复支付 | 同一订单出现第二笔成功的支付尝试时记为成功但不改订单，进入后台「异常支付」列表人工处理，不自动退款 |
| 租户 | 支付应用、渠道、单据、钱包都按租户隔离 |

### 1.2 非目标

- 真实渠道（微信、支付宝、任何聚合支付）的实现。字典中已有的 `wx_*`、`alipay_*` 编码保留，后台新建这些编码的渠道时提示「渠道未实现」。
- 对账文件下载、分账、提现、手续费结算。
- 前端工程（沿用总体设计）。

## 2. 服务结构

### 2.1 pay-api

- RPC 接口：`PayOrderApi`（创建、查询支付单）、`PayRefundApi`（发起、查询退款）、`PayTransferApi`（发起、查询转账）、`PayWalletApi`（查询钱包余额）。
- 消息主题常量与消息体：`pay.order.paid`、`pay.refund.success`、`pay.refund.failure`、`pay.transfer.success`、`pay.transfer.failure`。
- 错误码 `1_007_xxx_xxx`、枚举（单据状态、渠道编码、钱包业务类型等）。

### 2.2 pay-biz 包结构

| 包 | 内容 |
|---|---|
| `framework/pay/core/client` | 渠道接口 `PayClient`、渠道工厂 `PayClientFactory`、`MockPayClient`、`WalletPayClient` |
| `app` | 支付应用，绑定开放应用 |
| `channel` | 渠道配置，加密存储 |
| `order` / `refund` / `transfer` | 三类单据的生命周期 |
| `notify` | 渠道回调入口；订阅本服务发出的消息，转发给开放平台 |
| `wallet` | 钱包、流水、充值、充值套餐 |
| `job` | 关单、补查支付、补查退款、补查转账 |

### 2.3 接口前缀

| 前缀 | 用途 | 鉴权 |
|---|---|---|
| `/admin-api/pay/**` | 管理后台 | 管理员令牌 + 按钮权限 |
| `/app-api/pay/**` | 会员端收银台、钱包、充值 | 会员令牌 |
| `/open-api/pay/**` | 外部系统 | 网关签名校验 + 开放平台接口授权 |
| `/app-api/pay/notify/{order\|refund\|transfer}/{channelId}` | 渠道回调 | 免登录、免租户头，靠渠道验签 |
| `/app-api/pay/mock/confirm` | Mock 模拟支付确认页 | 免登录、免租户头，受 Mock 开关控制 |

## 4. 渠道层

### 4.1 渠道接口 `PayClient`

每条 `pay_channel` 对应一个渠道实例。

| 方法 | 作用 |
|---|---|
| `unifiedOrder` / `getOrder` / `parseOrderNotify` | 发起支付、主动查单、验签并解析支付回调 |
| `unifiedRefund` / `getRefund` / `parseRefundNotify` | 退款，含义同上 |
| `unifiedTransfer` / `getTransfer` / `parseTransferNotify` | 转账，含义同上 |

渠道不支持的能力抛「渠道不支持该操作」。

- 统一结果：状态（等待 / 成功 / 失败 / 关闭）、渠道单号、错误码与错误信息、回调原始报文。
- 支付展示方式：`QR_CODE`（二维码内容）、`URL`（跳转链接）、`FORM`（自动提交的表单）、`APP`（App 或小程序调起参数，JSON）、`NONE`（无需用户操作）。
- 下单请求带 `payMethod`（如 `wx_lite`、`alipay_qr`）：直连渠道忽略，聚合渠道据此选择支付方式。

### 4.2 渠道工厂 `PayClientFactory`

- 按渠道编号缓存实例；后台修改或删除渠道后，经 Redis 发布订阅通知所有 pay 实例清除该缓存。
- 渠道实现按渠道编码注册；新增渠道只需写一个实现类并注册。

### 4.3 Mock 渠道（`mock`）

- 配置：回调签名密钥；行为开关（`SUCCESS` 成功 / `FAIL` 支付失败 / `DROP_NOTIFY` 丢弃回调 / `DELAY` 延迟若干秒后回调）。
- 下单返回 `URL`，指向 `/app-api/pay/mock/confirm?no=<外部订单号>`。GET 返回一个带确认按钮的简单页面，POST 才执行确认，避免链接预取误触发。
- 确认后：在 Redis 记下该笔「已成功」（带过期时间，多实例查单一致），再按行为开关向渠道回调入口发送 HMAC-SHA256 签名的 HTTP 回调（请求体 + 时间戳），与真实渠道走同一条验签路径。
- 退款、转账同样异步回调，支持同样的行为开关。

### 4.4 钱包渠道（`wallet`）

- 下单要求订单带会员 `user_id`；同一事务内：原子扣减余额（`balance = balance - ? WHERE balance >= ?`）、写流水（业务编号为支付尝试的外部单号）、支付尝试置成功，展示方式 `NONE`。余额不足返回失败结果，不抛异常。
- 退款退回余额并写流水；转账给收款会员（`user_account` 为会员编号）的钱包入账并写流水。
- 无回调；查询方法按流水判断状态，供补查任务使用。
- 钱包充值订单不能用钱包渠道支付。

### 4.5 渠道配置安全

- `config` 整体加密存储，密钥取 `CCLOUD_ENCRYPT_KEY`。
- 后台查询时敏感字段返回 `***`；保存时敏感字段仍为 `***` 表示未修改，保留原值。

## 5. 单据生命周期

### 5.1 通用规则

- 状态流转一律条件更新（`WHERE id = ? AND status = 原状态`），影响 0 行即已被处理，按幂等返回。
- 业务消息与状态变更同一事务写 outbox。
- 渠道调用在数据库事务之外（钱包渠道除外）。渠道异常（如超时）只表示结果未知，单据保持等待，由补查任务确定，不因一次异常判为失败。
- 外部单号：前缀（P 支付 / R 退款 / T 转账）+ `yyyyMMddHHmmss` + Redis 自增序号，唯一索引兜底。

### 5.2 支付单

状态：0 待支付、10 支付成功、20 已退款、30 已关闭。支付尝试状态：0 等待、10 成功、30 关闭（渠道明确失败时记错误码并关闭）。

1. **创建**：经 `PayOrderApi` 或开放接口。同应用内商户订单号重复时，金额相同返回原订单，金额不同报错。
2. **提交支付**：校验订单待支付且未过期、渠道启用且属于该应用；先写支付尝试（等待）并提交，再调渠道下单，按结果更新支付尝试。
3. **支付成功**：渠道回调、同步结果、补查三条路径共用一个方法，同一事务内：支付尝试 等待 → 成功（已成功则直接返回）；订单 待支付 → 支付成功，写入成功尝试编号、渠道、支付方式、手续费；写 `pay.order.paid`。
4. **异常支付**：订单已被其他尝试支付或已关闭时，该尝试仍记成功，订单不变。后台「异常支付」列表按「尝试成功且订单的 `extension_id` 不是它」查询，不加字段。
5. **超时关单**：先向渠道逐个查询该订单等待中的支付尝试，确认都未支付才关闭订单与这些尝试；查到已支付的按第 3 步处理。

### 5.3 退款单

状态：0 等待、10 成功、20 失败。

1. **发起**：经 `PayRefundApi` 或开放接口。同应用内商户退款单号重复时返回原退款单。要求订单为支付成功；同一订单同一时间只允许一笔等待中的退款。
2. **预占额度**：`UPDATE pay_order SET refund_price = refund_price + ? WHERE id = ? AND refund_price + ? <= price`，再写退款单（等待），然后调渠道退款。
3. **成功**：退款单置成功；订单累计退款等于支付金额时置「已退款」，部分退款保持「支付成功」；写 `pay.refund.success`。
4. **失败**：退款单置失败，释放预占额度，写 `pay.refund.failure`。

### 5.4 转账单

状态：0 等待、5 处理中、10 成功、20 失败。经 `PayTransferApi` 或管理后台发起，同应用内商户转账单号唯一。渠道为 Mock 或钱包。结束时写 `pay.transfer.success` 或 `pay.transfer.failure`。

## 6. 通知

### 6.1 渠道回调入口

`/app-api/pay/notify/{type}/{channelId}`：忽略租户查出渠道，把上下文设为渠道所属租户；交渠道实现验签解析，再走 5.x 的统一处理方法；原始报文写入单据的 `channel_notify_data`；按渠道要求的格式应答。验签失败返回 400 并打 warn 日志。

### 6.2 内部消息

消息体：租户编号、支付应用编号与标识、单据编号、商户单号、金额、渠道编码、成功时间。业务服务订阅后按支付应用标识过滤自己的单据。

### 6.3 外部回调

pay 以消费者 `pay-open-notify` 订阅上述消息（幂等），支付应用绑定了开放应用时调用 `OpenNotifyApi.sendNotify`，事件名与主题同名。回调数据只含商户单号、平台单号、金额、状态、时间，不含渠道原始报文。调用 open 失败时抛出异常，消息重新投递；投递到 open 之后由 open 负责签名与重试。

## 7. 接口

### 7.1 会员端 `/app-api/pay/**`

查看待支付订单、可用渠道列表、提交支付、我的钱包、钱包流水、充值套餐列表、发起充值（返回支付订单编号）、我的充值记录。会员只能查看和支付 `user_id` 是自己的订单。

### 7.2 开放接口 `/open-api/pay/**`

创建支付单、查询支付单、提交支付（不可选钱包）、发起退款、查询退款。调用身份取自网关传来的开放应用，再找到绑定的支付应用；未绑定返回「开放应用未开通支付」。外部系统创建的支付单不带 `user_id`。

### 7.3 管理后台 `/admin-api/pay/**`

| 对象 | 功能 |
|---|---|
| 支付应用 | 增删改查，绑定开放应用 |
| 渠道 | 配置的增删改查 |
| 支付单 | 分页、详情（含全部支付尝试）、异常支付列表 |
| 退款单 / 转账单 | 分页、详情；发起转账 |
| 钱包 | 钱包分页、流水分页、调整余额 |
| 充值 | 套餐增删改查、充值记录分页、充值退款 |

## 8. 钱包

- **开通**：会员第一次访问时自动创建，靠唯一索引防并发重复。
- **充值**：会员选套餐或输入自定义金额（自定义金额无赠送），写充值记录，并在钱包充值应用下创建支付单。该应用的标识由 `ccloud.pay.wallet.recharge-app-key` 指定，默认 `wallet`（与演示数据一致）；租户未建该应用时提示「钱包充值未开通」。pay 订阅自己的 `pay.order.paid`，属于充值应用的订单：条件更新充值记录为已支付，入账「实付 + 赠送」，写流水。
- **充值退款**（后台发起）：先原子扣回到账总额，余额不足则拒绝；再对原支付单发起实付金额的退款；退款失败时把扣回的金额重新入账。
- **后台调整**：可增可减，必填原因；减少时要求余额充足；每次记流水（业务类型 6，业务编号为调整单号）。

## 9. 定时任务

XXL-Job 调度，按租户逐个执行，每次处理条数有上限。

| 任务 | 频率 | 处理对象 |
|---|---|---|
| `payOrderExpireJob` | 每分钟 | 过期仍待支付的订单（先查渠道再关闭） |
| `payOrderSyncJob` | 每分钟 | 创建超过 1 分钟仍等待中的支付尝试 |
| `payRefundSyncJob` | 每分钟 | 等待中的退款单 |
| `payTransferSyncJob` | 每分钟 | 等待中、处理中的转账单 |

## 10. 安全

- **Mock 开关** `ccloud.pay.mock-enabled`：只在 local、dev 环境配置为 true，不进 Nacos 配置包（与开放平台的 `allow-private-address` 做法一致）。关闭时后台不能新建或启用 Mock 渠道，渠道工厂拒绝创建 Mock 实例，模拟确认页返回 404。
- **订单归属**：会员端按 `user_id` 校验；开放接口按绑定的支付应用校验，只能操作本应用的单据。
- **渠道回调**：只认验签通过的请求；金额与渠道返回的金额不一致时拒绝并打 error 日志。
- **渠道配置**：加密存储，脱敏回显。
