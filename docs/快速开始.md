# 快速开始

## 准备

| 软件 | 版本 | 用途 |
|---|---|---|
| JDK | 21 | 编译与运行 |
| Maven | 3.9+ | 构建 |
| Docker | 含 compose v2（`docker compose version` 可用） | 应用镜像构建与运行 |
| 本机中间件 | MySQL 8.4、Redis 7 以上、Nacos 3、Zipkin、XXL-Job 3.4.2 | ccloud 直接连接本机已有的实例，不再自带一套 |

## 本机中间件

ccloud 的部署、测试与校验脚本都连接本机已有的中间件（Docker 容器），默认容器名与端口：

| 中间件 | 容器名 | 端口 | ccloud 使用的部分 |
|---|---|---|---|
| MySQL | `mysql` | 3306 | `ccloud` 库（业务）、`xxl_job` 库（调度中心）、`ccloud_test` 库（测试） |
| Redis | `redis` | 6379 | 1 号库（运行）、15 号库（测试）；0 号库留给其他项目 |
| Nacos | `nacos` | 8848 | `ccloud` 命名空间 |
| Zipkin | `zipkin` | 9411 | 接收链路数据 |
| XXL-Job 调度中心 | `xxl-job-admin` | 48180 | 执行器 `ccloud-system-server`、`ccloud-infra-server`、`ccloud-open-server`、`ccloud-pay-server` 及其任务 |

容器名不同时用 `CCLOUD_MYSQL_CONTAINER` 等环境变量指定（见 `scripts/lib/local-middleware.sh`）。
MySQL、Redis 的密码直接从容器配置读取；Nacos 账号写在 `~/.ccloud/middleware.env`（不进仓库）：

```bash
mkdir -p ~/.ccloud && printf 'NACOS_USERNAME=nacos\nNACOS_PASSWORD=你的密码\n' > ~/.ccloud/middleware.env && chmod 600 ~/.ccloud/middleware.env
```

端口、库编号、命名空间等非敏感配置在 `docker/.env` 中。本机没有这些中间件时，可以用 `docker/docker-compose.middleware.yml`
自带一套（容器名为 `ccloud-*`），再相应设置 `CCLOUD_*_CONTAINER`。

## 方式一：一键启动全部

```bash
scripts/docker-up.sh
```

脚本依次：

1. 检查本机中间件都在运行；
2. `ccloud` 库不存在时导入 `sql/mysql/ccloud.sql`（已存在则保留数据，`--reset-db` 重新导入）；
3. 登记 XXL-Job 执行器与任务（已登记则跳过）；
4. 在 Nacos 中创建 `ccloud` 命名空间，导入 `docker/nacos/config/` 下的配置包（已有的配置不覆盖）；
5. `mvn clean package` 打包 gateway、system、infra、member、open、pay、monitor，构建镜像并启动，等待全部健康检查通过（最多 8 分钟）；
6. 把 XXL-Job 调度中心接入 ccloud 的容器网络，调度中心才能回调执行器。

启动后先用管理员登录验证（见 [README](../README.md#接口与鉴权) 的示例），再打开 http://127.0.0.1:28080/doc.html 浏览接口文档。

停止（只停 ccloud 的 7 个应用，本机中间件及其中的 ccloud 数据不受影响）：

```bash
scripts/docker-down.sh
```

编排里所有应用固定使用 `dev` profile，所以 pay 开启了模拟支付（`ccloud.pay.mock-enabled=true`）：提交 Mock 渠道后返回确认页地址，
打开 `/app-api/pay/mock/confirm?no=...` 点击"确认支付"即模拟付款。这只是本机联调用的开关，**生产部署必须关闭**，见下文方式三的生产部署说明。

验证编排是否正常：

```bash
scripts/verify-docker.sh --full
```

## 方式二：只初始化，在 IDE 中运行服务

```bash
scripts/docker-up.sh init
```

完成上面第 1～4 步，不启动应用。然后在 IDE 中以 `local` profile（默认）运行：

| 启动类 | 端口 |
|---|---|
| `com.ccloud.module.system.SystemServerApplication` | 28081 |
| `com.ccloud.module.infra.InfraServerApplication` | 28082 |
| `com.ccloud.module.member.MemberServerApplication` | 28083 |
| `com.ccloud.module.open.OpenServerApplication` | 28084 |
| `com.ccloud.module.pay.PayServerApplication` | 28085 |
| `com.ccloud.gateway.GatewayServerApplication` | 28080 |
| `com.ccloud.monitor.MonitorServerApplication`（可选） | 28182 |

`local` profile 默认连接 `127.0.0.1` 上的 MySQL 3306、Redis 6379、Nacos 8848，关闭了登录验证码与 XXL-Job 执行器、开启了模拟支付，便于调试。
本机中间件的密码、库编号与命名空间用环境变量传入：`MYSQL_PASSWORD`、`REDIS_PASSWORD`、`REDIS_DATABASE=1`、
`NACOS_USERNAME`、`NACOS_PASSWORD`、`NACOS_NAMESPACE=ccloud`。建议先启动 system：infra、member、open、pay 启动后经 RPC 从 system 加载国际化文案，
system 未就绪时只记录警告，等 5 分钟后的定时刷新再加载。

## 方式三：从源码构建

```bash
mvn clean package -DskipTests
```

各应用的可执行 jar：

- `ccloud-gateway/target/ccloud-gateway.jar`
- `ccloud-monitor/target/ccloud-monitor.jar`
- `ccloud-module-system/ccloud-module-system-biz/target/ccloud-module-system-biz.jar`
- `ccloud-module-infra/ccloud-module-infra-biz/target/ccloud-module-infra-biz.jar`
- `ccloud-module-member/ccloud-module-member-biz/target/ccloud-module-member-biz.jar`
- `ccloud-module-open/ccloud-module-open-biz/target/ccloud-module-open-biz.jar`
- `ccloud-module-pay/ccloud-module-pay-biz/target/ccloud-module-pay-biz.jar`

运行时用 `SPRING_PROFILES_ACTIVE` 选择环境（`local` / `dev` / `prod`）。`prod` 不提供密码与密钥的默认值，须通过环境变量提供：

- 数据库与 Redis 的地址与密码、`CCLOUD_ENCRYPT_KEY`（字段加密）、`CCLOUD_MONITOR_PASSWORD`（监控面板）、
  `CCLOUD_CORS_ALLOWED_ORIGIN_PATTERNS`（网关允许的前端来源）——缺失时对应服务启动失败；
- `CCLOUD_INTERNAL_SIGN_SECRET`（网关与各服务共享的内部签名密钥）——网关缺失时启动失败；业务服务缺失时仍能启动，
  但会拒绝全部内部身份，所有登录请求都变成未登录。网关、system、infra、member、open、pay 必须配置同一个值。

生产部署的网络要求：业务服务端口（system 28081、infra 28082、member 28083、open 28084、pay 28085 等）只允许网关与其他服务访问，不得对外开放。
服务的 `/rpc-api/**` 不做认证，依赖网关阻断与网络隔离；其中 open 的 `get-by-key` 返回应用密钥原文，一旦能直连这些端口，就能取得全部开放应用的密钥。

生产部署还须做一件事：**导入初始化数据后删除开放平台的演示应用**。演示应用的密钥是用开发默认加密密钥加密入库的，
生产换了 `CCLOUD_ENCRYPT_KEY` 后无法解密（租户 1 的开放应用列表、详情、重置、删除都会报错）。导入后执行：

```sql
DELETE FROM open_app_api WHERE app_id = 1;
DELETE FROM open_app WHERE id = 1;
```

之后在管理后台 开放平台 → 开放应用 中创建真实的应用。

**支付的生产部署**同样有三件事：

1. **`ccloud.pay.mock-enabled` 必须为 `false`**。模拟支付只在 `local`、`dev` profile 中开启，`prod` profile 与默认值都是 `false`；
   不要把它写进环境变量或 Nacos（`scripts/verify-nacos.sh` 会拦截配置包中的 `mock-enabled: true`）。开着它，任何人都能用 Mock 渠道"支付"成功，白拿商品。
   docker 编排固定用 `dev` profile，因此只能用于本机联调，不能作为生产部署方式。
2. **删除演示数据中的支付渠道**。演示的三条渠道（两条 Mock、一条钱包）配置是用开发默认加密密钥加密入库的：Mock 渠道生产不可用，
   钱包渠道的配置换了 `CCLOUD_ENCRYPT_KEY` 后同样无法解密。导入后执行下面的语句，再在管理后台 支付管理 → 支付应用 中为各应用重新开通钱包渠道（配置填 `{}`）：

   ```sql
   DELETE FROM pay_channel WHERE id IN (1, 2, 3);
   UPDATE pay_app SET open_app_id = NULL WHERE open_app_id = 1;
   ```

   第二条语句解除演示支付应用 `mall` 与演示开放应用的绑定（后者按上文已被删除）。Mock 渠道遗留在库里时，后台只能改状态、费率与备注，不能再用。
3. **渠道回调地址前缀**。渠道回调（微信、支付宝或聚合支付接入后）打到 `{ccloud.pay.notify-base-url}/app-api/pay/notify/...`，默认值是本机网关 `http://127.0.0.1:28080`，
   生产须设为渠道能访问到的网关公网地址（环境变量 `CCLOUD_PAY_NOTIFY_BASE_URL`）。本期只有 Mock 与钱包渠道，没有外部回调，接入真实渠道时再配置。

若更换密钥后遇到「数据库加密字段解密失败：加密密钥与数据不一致」，说明库里仍有用旧密钥加密的数据。

运行测试：

```bash
mvn test
```

测试直接连接本机已有的 MySQL 与 Redis，不再临时启动容器：

- MySQL 只使用 `ccloud_test` 库，每次测试开始时按 `sql/mysql/ddl` 重建全部表；
- Redis 只使用 15 号库，每次测试开始时清空这一个库。0 号库禁止使用，也不会执行 `FLUSHALL`，本机 Redis 可与其他项目共用。

连接信息（默认 `127.0.0.1:3306`、`root`，`127.0.0.1:6379`）写在 `~/.ccloud/test.properties`，环境变量优先：

```properties
ccloud.test.mysql.password=你的 MySQL root 密码
ccloud.test.redis.password=你的 Redis 密码
# 可选：ccloud.test.mysql.host / port / username / database，ccloud.test.redis.host / port / database
```

对应的环境变量为 `CCLOUD_TEST_MYSQL_PASSWORD`、`CCLOUD_TEST_REDIS_PASSWORD` 等（键名大写、点换成下划线）。

`scripts/verify-sql.sh` 等 SQL 校验脚本通过 `docker exec` 在本机名为 `mysql` 的容器中执行（可用 `CCLOUD_MYSQL_CONTAINER` 指定容器名），
导入到 `ccloud_verify` 库，每次运行覆盖。

## 校验脚本

| 脚本 | 校验内容 |
|---|---|
| `scripts/verify-deps.sh` | 依赖版本一致性 |
| `scripts/verify-framework.sh` | 框架层不反向依赖业务模块 |
| `scripts/verify-sql.sh` | 全量 SQL 脚本与初始化数据 |
| `scripts/verify-codegen.sh` | 代码生成验收：在临时 git 工作区为两张演示表生成代码，合并错误码后真实编译并运行生成的测试 |
| `scripts/verify-docker.sh` | compose 编排、数据库与 Nacos、XXL-Job 初始化；`--full` 端到端 |
| `scripts/verify-nacos.sh` | Nacos 配置包导入与读回；`--full` 校验优先级与即时生效 |
| `scripts/verify-docs.sh` | 本文档与 README 的必备内容、引用与端口 |
| `scripts/verify-e2e.sh` | 端到端验收：经网关的三端登录、按钮权限、SSO、令牌、安全边界、会员运营（积分、等级、签到、地址、内部接口防重复）、基础设施（参数配置、文件上传与读取、头像、API 日志、数据源、数据库文档、代码生成、死信重投）、开放平台（应用与密钥、签名调用与脱敏、验签与授权失败、停用与重置立即生效、调用日志、回调验签与重试）、支付（外部系统经开放平台下单、Mock 支付并收到回调、退款、会员充值到账、钱包支付与退款、Mock 丢弃回调时由补查任务补回、回调入口保护；结束时清理并恢复演示会员的钱包）、文档、链路追踪、监控、定时任务（需先启动全部服务） |
| `scripts/verify-all.sh` | 依次执行以上全部校验（含构建与启动全部服务），任一失败即中止；加 `--with-tests` 先执行 `mvn test` |
