# 模块说明

## 分层与依赖规则

```
ccloud-dependencies   BOM，唯一的版本仲裁点，其他 pom 不写版本号
        ↑
ccloud-framework      通用能力（starter），不含业务、不依赖任何业务模块（scripts/verify-framework.sh 校验）
        ↑
ccloud-module-xxx     业务模块，固定拆为两个子模块：
  ├── xxx-api         对外契约：DTO、枚举、错误码、Feign 接口。可被其他业务模块依赖
  └── xxx-biz         实现：Controller、Service、Mapper、DO。可执行应用，不被任何模块依赖
```

业务模块之间只能依赖对方的 `-api`，经 Feign（`/rpc-api/**`）调用，不直接访问对方的表或服务类。因此任何非核心模块都可以整体删除。

## 框架层

| 模块 | 职责 |
|---|---|
| `ccloud-common` | 统一响应 `CommonResult`、业务异常与错误码、分页、枚举（用户类型、终端等）、JSON 与 Servlet 工具 |
| `starter-web` | 全局异常处理、统一响应、springdoc 分组（管理端 / 用户端 / 开放接口 / 内部接口）、XSS 过滤、API 访问日志、`@OperateLog` 操作日志 |
| `starter-security` | 解析网关签发的内部身份头并验签，建立登录身份；按路径校验用户类型；`@PreAuthorize("@ss.hasPermission(...)")` 权限表达式 |
| `starter-mybatis` | MyBatis Plus 配置、分页、逻辑删除（删除时 `deleted` 写入记录编号，唯一索引可带 `deleted`）、创建人 / 更新人填充、字段加密 `EncryptTypeHandler` |
| `starter-redis` | RedisTemplate 序列化、Redisson、带过期时间的缓存（`缓存名#1h`） |
| `starter-mq` | 本地消息表（Outbox，业务事务提交后投递，失败重投）、Redis Stream 消息收发与消费确认、未确认消息重投、幂等消费 |
| `starter-job` | XXL-Job 执行器接入 |
| `starter-excel` | Excel 导入导出、`@DictFormat` 字典翻译 |
| `starter-protection` | `@Idempotent` 幂等、`@RateLimiter` 方法级限流、`@ApiSignature` 接口签名 |
| `starter-biz-tenant` | 多租户：SQL 行级隔离、租户上下文与请求头解析、租户校验、`@TenantIgnore`、`@TenantJob`（任务逐租户执行）、按租户隔离的缓存 |
| `starter-biz-data-permission` | 部门数据权限（全部 / 本部门 / 本部门及以下 / 仅本人 / 自定义），自动改写 SQL |
| `starter-rpc` | OpenFeign 配置，调用时透传租户与登录身份（签名后的内部身份头） |
| `starter-monitor` | 链路编号 `trace-id` 响应头、Micrometer Tracing 与 Zipkin、Spring Boot Admin 客户端 |
| `starter-websocket` | WebSocket 会话管理与鉴权，多节点经 Redis Pub/Sub 广播消息 |
| `starter-i18n` | 国际化：MessageSource 与数据库文案、`Accept-Language` 解析、文案变更广播刷新 |
| `starter-test` | 单元测试基类：连接本机已有的 MySQL（`ccloud_test` 库，执行正式建表脚本）与 Redis（15 号库），每个用例事务回滚 |

业务服务需要实现框架定义的若干接口（权限、租户、字典、国际化文案、操作日志）。
system 直接查本地数据实现；其他服务经 RPC 调用 system 实现，见 `ccloud-module-member-biz` 的 `framework/contract` 包。

## 基础设施 infra

服务名 `ccloud-infra-server`，端口 28082。

### 功能

| 功能 | 路径 | 说明 |
|---|---|---|
| 参数配置 | `/admin-api/infra/config` | 全局一份，不分租户；按键名缓存，改动即时生效；系统内置参数不可删除、键名不可改；`system.user.init-password`（导入用户的初始密码）与 `system.auth.register-enabled`（管理员自助注册开关）由 system 读取 |
| 文件配置 | `/admin-api/infra/file-config` | 管理文件存储器，全局只有一个主配置，可测试、可切换主配置；配置变更经 Redis 通知所有节点重建客户端 |
| 文件 | `/admin-api/infra/file`、`/app-api/infra/file/upload` | 管理员、会员登录后可上传，默认上限 10MB；按文件内容识别类型，只收白名单类型，HTML / SVG / XML / 脚本一律拒绝；同内容只存一份，删除记录后无引用才删存储内容 |
| API 日志 | `/admin-api/infra/api-access-log`、`api-error-log` | 各服务把访问 / 异常日志发到 Redis Stream，infra 消费写库；请求中的密码等敏感字段已脱敏；异常日志可标记已处理 / 已忽略；定时清理过期日志 |
| 消息死信 | `/admin-api/infra/message-dead-letter` | 超过重试上限的本地消息与消费失败的 Stream 消息落库；可标记已处理，或重新投递到原主题（消费侧按消息编号幂等） |
| 数据源 | `/admin-api/infra/data-source-config` | 编号 0 为主数据源（取自应用配置，不可改）；其他数据源保存前先测试连接，密码加密存储，只支持 MySQL |
| 数据库文档 | `/admin-api/infra/db-doc` | 读取 `information_schema`，导出 HTML（带 CSP 头）与 Markdown |
| 代码生成 | `/admin-api/infra/codegen` | 见下文「代码生成」 |

定时任务统一在 XXL-Job 控制台管理，infra 不提供任务管理。

### 依赖

- infra 经 RPC 调用 system 实现框架的五个契约：权限、租户、字典、国际化、操作日志；
- system 经 `infra-api` 调用 infra 的 `ConfigApi`（按键名读取参数值：导入用户的初始密码、注册开关）和 `FileApi`（保存文件，头像上传用）；member 只调用 `FileApi`（头像上传用）；
- system、member、open 等业务服务把 API 日志写入 Redis Stream（主题 `infra.api-access-log`、`infra.api-error-log`），由 infra 消费，不直接调用 infra。

### 定时任务

登记在 XXL-Job 执行器 `ccloud-infra-server` 下（`scripts/docker-up.sh` 自动登记）：

| 任务处理器 | 周期 | 内容 |
|---|---|---|
| `apiAccessLogCleanJob` | 每天 03:00 | 删除超过保留天数（`ccloud.infra.api-log.access-retain-days`，默认 30）的访问日志 |
| `apiErrorLogCleanJob` | 每天 03:10 | 删除超过保留天数（`ccloud.infra.api-log.error-retain-days`，默认 90）的异常日志 |
| `redisStreamPendingMessageResendJob` | 每分钟 | 重投 infra 消费组中未确认的日志消息，超过重试上限写入死信 |

### 文件存储

文件配置支持三种存储器，在管理端「文件配置」中新增并设为主配置：

| 存储器 | 配置项 | 读取方式 |
|---|---|---|
| 数据库 | `domain` | 内容存 `infra_file_content`，经 `GET /admin-api/infra/file/{configId}/get/**` 免登录读取。默认主配置，开箱即用 |
| 本地磁盘 | `basePath`、`domain` | 写入 `basePath` 下，读取方式同上。`basePath` 须等于或位于受控根目录 `ccloud.infra.file.local-root` 之下（默认 `/app/files`，本机开发为 `~/.ccloud/files`），否则保存配置时报错；容器部署时 `basePath` 填 `/app/files`（挂载在 `infra-files` 数据卷上）。路径必须在 `basePath` 之内 |
| S3 兼容 | `endpoint`、`bucket`、`accessKey`、`accessSecret`、`region`、`pathStyle`、`domain` | 文件由存储桶（或其前置 CDN）直接读取，地址为 `domain` 加文件路径。适用于 AWS S3 与阿里云 OSS，存储桶的公开读权限需在云控制台配置 |

文件路径为 `yyyyMMdd/{内容 SHA-256}.{扩展名}`，不信任原文件名；返回配置时 `accessSecret` 显示为掩码，修改时提交掩码则沿用原值。

AWS S3 配置示例（虚拟主机风格，`pathStyle` 保持 `false`）：

```json
{
  "endpoint": "https://s3.ap-east-1.amazonaws.com",
  "bucket": "my-bucket",
  "accessKey": "AKIA...",
  "accessSecret": "...",
  "region": "ap-east-1",
  "pathStyle": false,
  "domain": "https://my-bucket.s3.ap-east-1.amazonaws.com"
}
```

阿里云 OSS 配置示例（OSS 兼容 S3 协议，同样 `pathStyle` 为 `false`）：

```json
{
  "endpoint": "https://oss-cn-hangzhou.aliyuncs.com",
  "bucket": "my-bucket",
  "accessKey": "LTAI...",
  "accessSecret": "...",
  "region": "cn-hangzhou",
  "pathStyle": false,
  "domain": "https://my-bucket.oss-cn-hangzhou.aliyuncs.com"
}
```

`domain` 也可以填存储桶前置的 CDN 域名。端点、地域、域名的具体写法以云厂商的 S3 兼容文档为准。保存前可用「测试」按钮上传一个小文件验证配置。

### 代码生成

只生成后端代码与 SQL，支持单表与树表，场景分管理后台与用户 App。使用步骤：

1. **导入**：「代码生成」中选择数据源，导入尚未导入的表。表名须为 `模块_业务` 格式（如 `member_point_record`），须有且只有一个 `bigint` 自增主键，字段须有注释；导入时按表结构推断模块、类名、字段类型与查询方式；
2. **编辑**：修改表与字段的生成配置（类名、作者、场景、模板类型、父菜单、各字段是否参与增改查与查询方式等）；表结构变化后用「同步」更新，已有的编辑保留；
3. **预览 / 下载**：预览得到每个文件的路径与内容；下载得到 zip 压缩包。每张表生成 11 个文件：DO、Mapper、Service、ServiceImpl、控制器、三个 VO、Service 测试、错误码片段、SQL；
4. **解压到仓库根目录**：压缩包的目录与本仓库一致，直接合并；
5. **合并错误码片段并重新编号**：把 `ErrorCodeConstants_{类名}.java.txt` 的内容并入对应模块 `-api` 的 `ErrorCodeConstants`，将预留区间 `1-099-xxx-xxx` 的默认编号改为本模块的段位，并把 SQL 里错误码文案的编号改成同样的值（两处必须一致）；
6. **执行 SQL**：确认 SQL 中的上级菜单编号正确后，执行 `sql/codegen/{表名}.sql`，登记菜单、按钮权限与错误码文案。

`scripts/verify-codegen.sh` 会为两张演示表（`infra_demo_student` 单表、`infra_demo_category` 树表）走完生成、合并错误码、编译、运行生成的测试的完整流程。

## 开放平台 open

服务名 `ccloud-open-server`，端口 28084。第三方系统以「应用」身份调用 `/open-api/**`，认证方式只有签名（HMAC-SHA256），协议与示例见 [接口鉴权说明](接口鉴权说明.md#开放接口-open-api)。

### 功能

| 功能 | 路径 | 说明 |
|---|---|---|
| 开放应用 | `/admin-api/open/app` | 创建应用（系统生成 AppKey 与密钥，密钥加密存储，只在创建与重置时返回一次）、状态、过期时间、每秒请求上限、IP 白名单、回调地址；重置密钥；整体替换可调接口；发送测试回调。按租户隔离，租户管理员自管 |
| 接口目录 | `/admin-api/open/api` | 可开放的接口清单，一条「请求方法 + 路径」一个接口，路径须以 `/open-api/` 开头。全部租户共用，增删改仅限系统租户（错误码 `1005000000`）；关闭或删除后所有应用对它的调用返回 403 |
| 调用日志 | `/admin-api/open/api-log` | 开放接口调用明细（应用、接口、请求参数、业务结果、耗时、客户端 IP、链路编号），分页与导出；参数已脱敏，不记录响应内容 |
| 回调日志 | `/admin-api/open/notify-log` | 回调通知的发送记录与重试状态（待通知、成功、失败待重试、放弃）；失败待重试或放弃的记录可手工「重新通知」 |

没有令牌模式，也没有每日总量配额：配额只做每秒限流，由网关按应用令牌桶执行。

### 依赖

- open 经 RPC 调用 system 实现框架的五个契约：权限、租户、字典、国际化、操作日志。其中「是否系统租户」（接口目录增删改的校验）是租户契约的 `isSystemTenant`；
- 网关经 `OpenAppApi`（`GET /rpc-api/open/app/get-by-key`）读取应用快照，本地缓存 60 秒（未找到缓存 10 秒）；open 在应用、授权、接口目录变更后向 Redis 频道 `ccloud:open:app:invalidate` 广播，各网关实例即时清除缓存。open 不可用且网关没有缓存时，开放接口返回 503；
- 业务服务经 `OpenNotifyApi`（`POST /rpc-api/open/notify/send`，`{appId, eventId, event, data}`）向应用发回调，返回回调日志编号。`eventId` 可选，非空时按它去重（相同事件编号重复发送只记一条回调），为空由平台生成。事件类型登记在 `OpenNotifyEvents`：测试事件 `open.test` 与 pay 的 5 个支付事件，见下文「支付 pay」；
- 调用日志：提供开放接口的业务服务（目前是 member）在自己的 `ApiLogFrameworkServiceImpl` 中，把开放应用的访问日志另发一份到 Redis Stream 主题 `open.api-log`，open 消费后按应用租户写库。member 只依赖 `open-api` 取主题常量，不调用 open 的接口；
- 身份：开放应用的用户类型是 `OPEN_APP(3)`，由网关签发内部身份头。框架按路径校验用户类型：`/open-api/**` 只接受开放应用，开放应用在其他路径一律按未登录处理。

### 定时任务

登记在 XXL-Job 执行器 `ccloud-open-server` 下（`scripts/docker-up.sh` 自动登记）：

| 任务处理器 | 周期 | 内容 |
|---|---|---|
| `openNotifyRetryJob` | 每 15 秒 | 发送到期的回调（待通知与失败待重试，每批最多 100 条，跨租户），按退避间隔重试，超过次数放弃 |
| `openApiLogCleanJob` | 每天 03:20 | 删除超过保留天数（`ccloud.open.api-log.retain-days`，默认 30）的调用日志，以及同样过期且已成功或已放弃的回调日志 |
| `redisStreamPendingMessageResendJob` | 每分钟 | 重投 open 消费组中未确认的调用日志消息，超过重试上限写入死信 |

### 回调配置与生产要求

| 配置项（`ccloud-open-server.yaml`） | 默认 | 说明 |
|---|---|---|
| `ccloud.open.notify.allow-private-address` | `false` | 回调地址可否指向回环、内网等地址。默认拒绝，防止借回调探测内网（SSRF）。本地开发与 docker 联调时回调接收方在本机，`local`、`dev` profile 设为 `true`；**该开关只在 profile 中设置，Nacos 配置包不得包含**（配置包优先于 profile，写入会覆盖各环境；`scripts/verify-nacos.sh` 会拦截；已导入过旧配置包的环境须在 Nacos 控制台手工删除该行，见 `docker/nacos/README.md` 约定 5）。**生产环境必须为 `false`**（`prod` profile 与默认值均为 `false`）。云元数据地址（`169.254.0.0/16`、`fd00:ec2::254`，含 IPv4 映射等写法）不受此项影响，任何配置下都拒绝 |
| `ccloud.open.notify.connect-timeout` / `read-timeout` | `5s` | 回调的连接与读取超时；整体不超过两者之和 |
| `ccloud.open.api-log.retain-days` | `30` | 调用日志与已结束的回调日志保留天数 |

容器内的 open 访问宿主机上的回调接收方，地址写 `host.docker.internal:端口`。

## 支付 pay

服务名 `ccloud-pay-server`，端口 28085。提供与渠道无关的支付中心：本期用 Mock 与钱包两个渠道在本地走通「下单 → 支付 → 通知 → 退款 → 转账」，
以后接聚合支付或直连微信、支付宝时只需新增一个渠道实现。设计见[支付模块设计](superpowers/specs/2026-10-12-pay-design.md)，其中「实现与设计的差异」一节记录了实现中的取舍。

### 功能

| 功能 | 路径 | 说明 |
|---|---|---|
| 支付应用 | `/admin-api/pay/app` | 每个接入支付的业务方一条，按应用标识区分；可绑定一个开放应用（`openAppKey`，一个开放应用最多绑定一个支付应用），绑定后外部系统才能经开放平台调用支付开放接口并收到回调；应用下有支付单时不可删除 |
| 渠道 | `/admin-api/pay/channel` | 应用下的渠道配置，一个应用每种编码一条；配置加密存储，回显时敏感字段为 `***`，修改时敏感字段提交 `***` 沿用原值；本期实现 `mock` 与 `wallet`，其他编码（`wx_*`、`alipay_*`）新建时提示「渠道未实现」 |
| 支付单 | `/admin-api/pay/order`、`/app-api/pay/order`、`/app-api/pay/channel/list` | 管理端：分页、详情（含全部支付尝试）、异常支付列表（订单已被其他尝试支付或已关闭，之后才到账的尝试，需人工处理，不自动退款）；会员端：只能查看和支付付款人是自己的订单，提交支付时选渠道，钱包支付即时成功 |
| 退款单 | `/admin-api/pay/refund` | 分页与详情。发起退款经 `PayRefundApi`（内部服务）或开放接口（外部系统）；同一订单可多次部分退款，合计不超过支付金额，同一时间只允许一笔处理中的退款 |
| 转账单 | `/admin-api/pay/transfer` | 管理端发起、分页、详情；渠道为 Mock 或钱包（钱包转账的收款账号是会员编号）。转账不对外部系统开放 |
| 钱包 | `/admin-api/pay/wallet`、`/admin-api/pay/wallet-transaction`、`/app-api/pay/wallet`、`/app-api/pay/wallet-transaction` | 会员第一次访问时自动开通；余额变更都有流水，同一业务单据对同一钱包只能入账一次；管理端可分页查询并调整余额（可增可减，必填原因） |
| 钱包充值 | `/admin-api/pay/wallet-recharge-package`、`/admin-api/pay/wallet-recharge`、`/app-api/pay/wallet-recharge-package`、`/app-api/pay/wallet-recharge` | 会员选套餐（实付加赠送，如「充 100 送 10」到账 110 元）或填自定义金额（无赠送），在充值应用下生成支付单，付款后入账；管理端可对已支付的充值退款（先扣回到账总额再退实付金额） |
| 开放接口 | `/open-api/pay/**` | 外部系统用：`order/create`、`order/get`、`order/submit`、`refund/create`、`refund/get`，协议见[接口鉴权说明](接口鉴权说明.md#支付开放接口) |
| 渠道回调 | `/app-api/pay/notify/{order\|refund\|transfer}/{channelId}` | 免登录、免租户头，靠渠道验签；验签失败或业务校验不通过返回 400，渠道不存在 404，渠道配置不可用等服务端问题返回 500（让渠道重试） |
| Mock 确认页 | `/app-api/pay/mock/confirm` | 仅开启模拟支付的环境存在：`GET` 展示商品与金额，`POST ?no=` 确认支付，避免链接预取误触发 |

### 渠道层

渠道层在 pay-biz 的 `framework/pay/core/client` 包（与 system 的短信客户端、infra 的文件客户端结构一致，不做成框架 starter）：

- `PayClient`：每条渠道配置对应一个实例，方法为 `unifiedOrder` / `getOrder` / `parseOrderNotify`，退款、转账同构；渠道不支持的能力抛「渠道不支持该操作」。
  统一结果为等待 / 成功 / 失败，支付的展示方式有 `QR_CODE`、`URL`、`FORM`、`APP`、`NONE`；下单带 `payMethod`，直连渠道忽略，聚合渠道据此选择支付方式；
- `PayClientProvider`：每个渠道实现一个，声明为 Spring Bean 即注册，新增渠道只需写 `PayClientProvider`、配置类和 `PayClient`；
- `PayClientFactory`：按渠道编号缓存实例，每次取用时比对库中的编码与配置，变化即重建，所以改配置、删渠道不需要通知其他实例；解析与校验配置，脱敏回显，保存时合并 `***`；
- `mock`：配置 `notifySecret`（至少 16 位，敏感字段）、`behavior`（`SUCCESS` 成功并立即回调 / `FAIL` 支付失败并回调 / `DROP_NOTIFY` 成功但不回调，用于验证补查 / `DELAY` 成功并延迟回调）、`delaySeconds`（`DELAY` 的延迟秒数，1–60，默认 3）。
  下单返回 `URL`，指向确认页；单据状态存 Redis（多实例查单一致），回调用 `X-Mock-Timestamp`、`X-Mock-Sign`（`Base64(HmacSHA256(notifySecret, 时间戳 + "\n" + 请求体))`）签名，与真实渠道走同一条验签路径。
  由 `ccloud.pay.mock-enabled` 控制是否注册，关闭时后台不能新建或启用 Mock 渠道、确认页返回 404；
- `wallet`：无配置。下单要求订单带会员付款人，原子扣减余额并写流水，余额不足返回失败结果；退款退回余额，转账给收款会员的钱包入账；没有回调，查询方法按流水判断状态，供补查使用。
  钱包充值订单不能用钱包支付。

### 单据状态

| 单据 | 状态 |
|---|---|
| 支付单 `pay_order` | 0 待支付、10 支付成功、20 已退款（累计退款等于支付金额）、30 已关闭 |
| 支付尝试 `pay_order_extension` | 0 等待、10 成功、30 关闭（渠道明确失败也记为关闭）。每提交一次支付生成一条，一个订单可有多次尝试 |
| 退款单 `pay_refund` | 0 等待、10 成功、20 失败 |
| 转账单 `pay_transfer` | 0 等待、5 处理中、10 成功、20 失败 |
| 钱包流水 `pay_wallet_transaction` | 业务类型：1 充值、2 充值退款、3 支付、4 支付退款、5 提现（本期不用）、6 后台调整、7 转账入账 |

状态流转一律条件更新（`WHERE id = ? AND status = 原状态`），影响 0 行即已被他人处理，按幂等返回。渠道调用不在数据库事务内（钱包渠道自带的本地事务除外）；
渠道调用抛异常只表示结果未知，单据保持等待，由补查任务确定，不因一次异常判为失败。所有表按租户隔离，金额一律为整数分。

### 消息与外部回调事件

状态变更与 outbox 消息在同一事务提交，经 Redis Stream 投递（主题常量与消息体在 `pay-api` 的 `mq/message` 包）：

| 主题 | 时机 |
|---|---|
| `pay.order.paid` | 支付单支付成功 |
| `pay.refund.success`、`pay.refund.failure` | 退款成功、失败 |
| `pay.transfer.success`、`pay.transfer.failure` | 转账成功、失败 |

pay 自己订阅这些主题（消费方用 `IdempotentConsumer` 幂等，一条消息的各项处理各自幂等，其中一项失败时消息重投、已完成的项被跳过）：

- 消费者 `pay-wallet-recharge`：钱包充值应用的支付成功入账、充值退款结果处理；
- 消费者 `pay-open-notify`：支付应用绑定了开放应用时，调用 `OpenNotifyApi.sendNotify` 回调外部系统，事件名与主题同名，**事件编号取 outbox 消息编号**（消息重投时开放平台按事件编号去重，外部系统只收到一次）。签名与重试由 open 负责，`data` 字段见[接口鉴权说明](接口鉴权说明.md#支付事件)。

其他业务服务（如日后的商城）订阅同样的主题，按支付应用标识 `appKey` 过滤自己的单据。消息缺少租户编号，或退款、转账消息的状态与主题不符，监听器会抛异常，消息重投若干次后进入死信，而不是静默确认。

### 定时任务

登记在 XXL-Job 执行器 `ccloud-pay-server` 下（`scripts/docker-up.sh` 自动登记），路由为单实例、阻塞策略为串行。任务跨租户扫描，逐条在该单据所属租户下处理；按编号游标分页，一次运行处理完当前全部积压：

| 任务处理器 | 周期 | 内容 |
|---|---|---|
| `payOrderExpireJob` | 每分钟（0 秒） | 关闭已过期仍待支付的订单：先向渠道查询每个等待中的支付尝试，确认都未支付才关闭，查到已支付的按支付成功处理 |
| `payOrderSyncJob` | 每分钟（10 秒） | 补查创建超过 `sync-delay` 且仍在等待的支付尝试，覆盖回调丢失 |
| `payRefundSyncJob` | 每分钟（20 秒） | 补查等待中的退款单（钱包渠道查不到流水时按退款单号幂等重发） |
| `payTransferSyncJob` | 每分钟（40 秒） | 补查等待中、处理中的转账单 |
| `redisStreamPendingMessageResendJob` | 每分钟（30 秒） | 重投 pay 消费组中未确认的消息，超过重试上限写入死信 |

### 依赖

- pay 经 RPC 调用 system 实现框架的五个契约：权限、租户、字典、国际化、操作日志；
- 绑定开放应用时经 `OpenAppApi` 校验开放应用存在且属于当前租户，经 `OpenNotifyApi` 发回调；网关经 open 读取应用快照后，把开放接口的调用转发给 pay；
- 其他服务经 `pay-api` 的 `PayOrderApi`、`PayRefundApi`、`PayTransferApi`、`PayWalletApi`（`/rpc-api/pay/**`）创建与查询支付单、退款、转账，查询钱包余额（钱包充值应用的订单与退款只能经充值流程，RPC 下单与退款会被拒绝）；`pay-api` 同时提供错误码（`1_007_xxx_xxx`）、枚举与消息体。

### 配置项

| 配置项 | 默认 | 说明 |
|---|---|---|
| `ccloud.pay.mock-enabled` | `false` | 模拟支付开关。**只在 `local`、`dev` profile 中为 `true`，不进 Nacos 配置包**（`scripts/verify-nacos.sh` 会拦截）。docker 编排固定使用 `dev` profile，所以编排里的 pay 开启了模拟支付，仅用于本机联调。**生产环境必须为 `false`，并删除演示数据中的 Mock 渠道**，见[快速开始](快速开始.md#方式三从源码构建) |
| `ccloud.pay.notify-base-url` | `http://127.0.0.1:28080` | 渠道回调地址前缀（网关地址），回调地址为 `{前缀}/app-api/pay/notify/{order\|refund\|transfer}/{渠道编号}`；`dev` 为 `http://ccloud-gateway:28080`（容器内的 pay 经网关接收 Mock 回调）。属于各环境的部署地址，不放进配置包 |
| `ccloud.pay.wallet.recharge-app-key` | `wallet` | 钱包充值所用支付应用的标识，各租户在后台自建同名应用并开通渠道；租户未建时发起充值提示「钱包充值未开通」。该应用不对开放平台开放 |
| `ccloud.pay.wallet.recharge-expire` | `2h` | 充值支付单的有效期 |
| `ccloud.pay.job.batch-size` | `100` | 定时任务每页处理的条数 |
| `ccloud.pay.job.sync-delay` | `1m` | 支付尝试创建多久后仍在等待才主动查单 |
| `ccloud.pay.job.sync-window` | `1d` | 只补查这段时间内创建的支付尝试，更早的交给超时关单 |
| `ccloud.pay.job.time-budget` | `50s` | 补查、关单任务单次运行的时间预算，用完即结束、余下留给下一轮；须小于 XXL-Job 登记的执行超时（60 秒）。不在配置包中，需要时再加 |

`recharge-app-key`、`recharge-expire`、`batch-size`、`sync-delay`、`sync-window` 五项在 Nacos 配置包 `ccloud-pay-server.yaml` 中，修改后重启 pay 生效。
